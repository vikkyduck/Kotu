# Если сервер умер

Платформа живёт на одной машине. Запасной нет — это осознанный компромисс, а не
недосмотр: второй сервер стоит денег и внимания, а пользователь пока один. Цена
компромисса известна заранее: авария означает не потерю данных, а несколько
часов простоя. Ниже — как эти часы прожить.

Оценка по шагам: новый сервер 10 минут, установка 20 минут, восстановление
данных 5 минут, домен 10–40 минут (сколько будет обновляться DNS).

---

## Что у вас есть на руках

| Что | Где |
|---|---|
| Код | GitHub: `git@github.com:vikkyduck/Kotu.git` |
| База данных | `~/kotu-backups/db/kotu-ДАТА.dump` (забирается сама, ежедневно в 13:30) |
| Файлы: книги, аудио, картинки и архив прежних версий | `~/kotu-backups/data/` (архив — `data/archive`) |
| Секреты и конфиги | `~/kotu-backups/files/config-ДАТА.tar.gz` |
| Ключ доступа | `~/.ssh/id_ed25519` |

Проверить свежесть копии: `ls -la ~/kotu-backups/db` — дата последнего дампа.
Забрать прямо сейчас: `./ops/pull-backup.sh`.

---

## Порядок восстановления

**1. Новый сервер.** В панели Timeweb создать машину с Ubuntu (не меньше 4 ГБ
памяти — на ней работают распознавание речи и эмбеддинги). Записать её адрес.

**2. Доступ.** Положить на неё свой ключ:

```
ssh-copy-id root@НОВЫЙ_АДРЕС
```

**3. Установка.** Дальше проще всего позвать меня: «сервер умер, вот новый
адрес — разверни платформу из бэкапа». Развёртывание описано в `DEPLOY.md`:
Postgres с расширением pgvector, Node, nginx, три локальных сервиса (Whisper,
маскировка имён, эмбеддинги), systemd-юниты и HTTPS.

**4. Данные.** База разворачивается одной командой:

```
sudo -u postgres createdb kotu && sudo -u postgres pg_restore -d kotu --no-owner kotu-ДАТА.dump
```

Файлы возвращаются на место копированием (`-H` — архив и рабочие каталоги снова делят одну
копию, а не две):

```
rsync -aH ~/kotu-backups/data/ root@НОВЫЙ_АДРЕС:/opt/kotu/
```

Секреты — из архива `config-ДАТА.tar.gz`: в нём `.env` со всеми ключами.

Архив прежних версий (схема `archive`) приезжает вместе с базой. Но `--no-owner` делает
владельцем всего `postgres`, а приложению нужно владеть своими таблицами: без этого оно не
прочитает данные, а архив не включится (триггер и `CREATE OR REPLACE` может только владелец).
Сразу после `pg_restore` — передать всё пользователю приложения (имя — из `DATABASE_URL` в
`.env`, обычно `kotu`; роль должна уже быть: `sudo -u postgres createuser -P kotu`):

```
sudo -u postgres psql -d kotu -v ON_ERROR_STOP=1 <<'SQL'
-- Все таблицы public и archive (последовательности id переходят вместе с ними),
-- схема архива и её функции. Этот же текст прогоняет тест deploy-owner-check.test.ts.
ALTER SCHEMA archive OWNER TO kotu;
DO $$ DECLARE r record; BEGIN
  FOR r IN SELECT schemaname, tablename FROM pg_tables WHERE schemaname IN ('public', 'archive') LOOP
    EXECUTE format('ALTER TABLE %I.%I OWNER TO kotu', r.schemaname, r.tablename);
  END LOOP;
  FOR r IN SELECT p.oid::regprocedure AS f FROM pg_proc p
             JOIN pg_namespace n ON n.oid = p.pronamespace WHERE n.nspname = 'archive' LOOP
    EXECUTE format('ALTER FUNCTION %s OWNER TO kotu', r.f);
  END LOOP;
END $$;
SQL
```

Проверка — та же, что делает `deploy.sh` перед выкаткой; после `systemctl restart kotu`
`https://psy3107.ru/api/healthz` должен показывать `"archive":"ok"`.

**5. Домен.** В панели, где живёт домен `psy3107.ru`, поменять A-запись на новый
адрес. Пока DNS обновляется, платформа уже доступна по адресу сервера.

## Чтобы это работало, когда понадобится

- **Копия должна быть свежей.** Она забирается сама каждый день в 13:30, если
  компьютер включён. Если он был выключен, macOS запустит задачу при следующем
  включении. Проверка — дата файлов в `~/kotu-backups/db`.
- **Репетиция раз в несколько месяцев.** С компьютера:
  `ssh root@5.129.198.180 bash -s < ~/kotu/ops/restore-check.sh` —
  разворачивает свежий дамп во временную базу, показывает, сколько строк доехало,
  и убирает её за собой. Рабочую базу не трогает.
- **Что здесь только пополняется, а что — зеркало.** Дампы `db/`, конфиги `files/`,
  архив файлов `data/archive` и снимки `predeploy/` на этом компьютере не удаляются и не
  перезаписываются никогда — даже когда на сервере их уже нет (место на диске
  убывает — решать вам). Зеркалами сервера
  остаются только `data/library`, `data/uploads`, `data/decks`: удалённое в платформе уходит
  и отсюда (но лежит в `data/archive`), поэтому своего в них не кладите.
- **Зеркала синхронизируются, только если сервер жив**: на нём есть свежий (моложе 2 суток)
  дамп `kotu-*.dump` и каталог `data/archive`. Иначе `pull-backup.sh` забирает только новое,
  ничего здесь не удаляет, громко предупреждает `!!! ВНИМАНИЕ: сервер не похож на живой` и
  завершается с кодом 2 — тогда сначала разобраться с бэкапом на сервере.
- **Копия — это зона А.** В ней настоящие имена и записи сеансов. Её можно
  держать у себя и в российском хранилище, но нельзя класть в зарубежное облако.

## Как отключить ежедневную выгрузку

```
launchctl bootout gui/$(id -u)/ru.psy3107.backup-pull
```

Файл задачи: `~/Library/LaunchAgents/ru.psy3107.backup-pull.plist`,
лог: `~/Library/Logs/psy3107-backup.log`.
