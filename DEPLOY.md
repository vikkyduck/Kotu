# Kotu — прод-топология (июль 2026)

- **Приложение**: **https://psy3107.ru** на Timeweb VDS `5.129.198.180` (nginx-сайт `psy3107`: статика `/opt/kotu/public` + `/api` → systemd `kotu` на 127.0.0.1:5010). Секреты: `/opt/kotu/.env`.
- **Выкатка**: `./deploy.sh` (сборка локально, rsync артефактов, рестарт).
- **OpenAI**: api.openai.com блокирует РФ-IP, поэтому запросы идут через прокси на DigitalOcean-дроплете **vikky-ai-server** (`206.189.181.64`, NYC1):
  - systemd `openai-proxy`, `/opt/openai-proxy/proxy.mjs` (node, без зависимостей), порт **8443**, TLS самоподписанный (`NODE_EXTRA_CA_CERTS=/opt/kotu/openai-proxy-ca.pem` в юните kotu);
  - принимает соединения только с IP Timeweb VDS (allowlist в коде + ufw);
  - в `.env`: `AI_INTEGRATIONS_OPENAI_BASE_URL=https://206.189.181.64:8443/v1`.
- На том же дроплете живёт посторонний сервис `ai-agent` (порт 3000) — не трогать.
- БД: Postgres `kotu` на Timeweb VDS; миграции — drizzle push через ssh-туннель, только вручную и по порядку из «Миграция схемы» ниже.

## Локальный Whisper (2026-07-22)

Транскрибация переведена с облачного `gpt-4o-transcribe` на **локальный openai/whisper** на самом Timeweb VDS:

- `/opt/whisper` — venv (torch CPU), пакет `openai-whisper` с GitHub, `server.py` (FastAPI, OpenAI-совместимый `POST /v1/audio/transcriptions`), кэш модели в `/opt/whisper/cache`
- systemd **kotu-whisper** — uvicorn на 127.0.0.1:9010, модель из env `WHISPER_MODEL` (сейчас `base`), язык `ru`, MemoryMax=1400M (на VDS всего 2 ГБ + 2 ГБ своп)
- nginx **kotu-ai-router** (127.0.0.1:8444): `/v1/audio/*` → Whisper (таймаут 30 мин), остальные `/v1/*` (chat-структурирование) → по-прежнему OpenAI через DO-прокси
- `/opt/kotu/.env`: `AI_INTEGRATIONS_OPENAI_BASE_URL=http://127.0.0.1:8444/v1`

**Вернуться на облачную транскрибацию**: `AI_INTEGRATIONS_OPENAI_BASE_URL=https://206.189.181.64:8443/v1` + `systemctl restart kotu`.
**Качество/скорость**: base ≈ 0.5× длительности записи на этом CPU; точность ниже gpt-4o-transcribe. Модель покрупнее (`small`) в 2 ГБ RAM не влезает — нужен апгрейд тарифа.

## Апгрейд: faster-whisper large-v3-turbo (2026-07-22, вечер)

- Тариф VDS поднят до 8 CPU / 12 ГБ RAM / 100 ГБ NVMe (2900 ₽/мес, оплачен год)
- Движок заменён на **faster-whisper** (CTranslate2 int8) с моделью **large-v3-turbo** в БАТЧЕВОМ режиме (`BatchedInferencePipeline`, batch=8) — на QEMU-vCPU этой ноды батчинг даёт 4–5x против последовательного декодера (RTF 0.20 против ~1.0)
- Замер end-to-end через Кота: запись 63 мин → **15 мин 11 сек** (вкл. gpt-оформление); полтора часа ≈ 21–22 мин
- env сервиса: `WHISPER_MODEL=large-v3-turbo`, `WHISPER_BATCH=8`, `HF_HOME=/opt/whisper/cache` (модель с Hugging Face), MemoryMax=8G
- Прежний вариант (openai/whisper base) больше не используется; venv общий

## Очередь задач (2026-07-30)

Фоновая работа больше не гибнет при перезапуске сервера.

- Таблица `jobs` (kind, entity_id, payload, status, attempts, run_after, last_error). Выдача задач — `FOR UPDATE SKIP LOCKED`, без Redis и брокеров
- Воркер живёт в процессе api-server: при старте `requeueOrphans()` возвращает в очередь задачи, оборванные прошлым рестартом, дальше — цикл `claimNext → run → finish`
- Повторы: до 3 попыток, паузы 30 с и 120 с; после исчерпания запись помечается ошибкой с человеческой формулировкой
- Загруженное аудио теперь в `/opt/kotu/uploads` (переживает рестарт и чистку /tmp). С 23.09.2026 оно НЕ удаляется ни после успеха, ни после провала — только когда владелица удаляет запись, и тогда уходит в архив `/opt/kotu/archive` (см. «Архив» ниже)
- Грабли: сырой SQL в drizzle возвращает колонки как есть (`entity_id`), camelCase не появляется — поэтому claimNext берёт только id, а объект читается через query builder

## Архив (2026-09-23)

Решение владелицы: стирать нельзя ничего — ни кодом, ни деплоем, ни бэкапом.

- Строки: схема `archive` в базе `kotu`. Триггеры `kotu_archive` на transcriptions, folders, documents, decks, deck_slides, deck_images, style_packs, lectures, lecture_sections, lecture_sources пишут прежнюю строку в `archive.rows` при удалении (и каскадном тоже) и при правке содержимого. Первый старт кладёт туда же всё текущее (`op='INITIAL'`). Ставит всё это сам сервер на каждом старте (`lib/archive.ts`); схему заранее создаёт `deploy.sh` от postgres с владельцем-приложением
- Файлы: `/opt/kotu/archive/<sha[0:2]>/<sha256>` — жёсткие ссылки на файлы library/uploads/decks (место не занимают), учёт в `archive.files` и `archive.file_events`. Перед любым rm файла данных он сначала ложится в архив, иначе rm не выполняется. Перезапись файлов — только через временный файл и rename. Сверка каталогов с архивом — на старте и каждые 6 часов
- `GET /api/healthz` → `{"status":"ok","archive":"ok"}`. `archive:"off"` — архив не включился: сервер отвечает, но только на чтение (очередь задач и стартовые сверки не запускаются, изменения и удаления — 503) и пробует включить архив раз в минуту. `deploy.sh` ещё до заливки проверяет, что таблицы данных и архива принадлежат пользователю приложения (иначе триггер не поставить), а выкатку без `archive:"ok"` бракует. Команды отката она не печатает намеренно — см. «Откат» ниже; `archive:"pending"` после двух минут ожидания (первое включение со снимком всех таблиц) — не провал: проверить healthz через минуту
- Бэкап: `/opt/backups/data/archive` — копия архива, которая только пополняется (`--ignore-existing`, без `--delete`); файл рабочего каталога и его объект в архиве лежат в бэкапе одной копией (`-H`). Снимки `/opt/backups/predeploy` не ротируются; код в них — тоже жёсткими ссылками. `deploy.sh` и ночной бэкап предупреждают, если на диске меньше 10 ГБ
- Самопроверка: при старте и раз в 6 ч сервер смотрит в `pg_trigger`, на месте ли триггеры архива (построчный и запрет TRUNCATE) на всех 10 таблицах; нет — сразу только чтение и повторная установка. Попытка включения ограничена 60 с. Очередь не берёт задачи, пока архив не `ok`
- `drizzle push` схему `archive` не видит и не трогает (управляет только `public`). Если push когда-нибудь пересоздаст таблицу, триггер пропадёт; сервер заметит это сам при сверке (раз в 6 ч) и уйдёт в «только чтение», пока не поставит его снова, — но правки до этого момента мимо архива. Поэтому после push — сразу `systemctl restart kotu` (см. «Миграция схемы»)

### Миграция схемы

`drizzle push` (когда меняется `lib/db/src/schema`) — только вручную, никогда автоматически
(`scripts/post-merge.sh` его больше не зовёт). push может сделать `DROP COLUMN`, пересоздать таблицу
или предложить `truncate` — и всё это мимо архива строк. Порядок:

1. **Дамп до push**: `./deploy.sh` (снимок в `/opt/backups/predeploy`) или на сервере
   `sudo -u postgres pg_dump -Fc kotu > /opt/backups/predeploy/push-$(date +%Y%m%d-%H%M%S).dump`.
2. **push** через ssh-туннель — рецепт в конце `deploy.sh`. Если предлагает truncate — отказаться:
   TRUNCATE таблиц данных запрещён триггером `kotu_archive_truncate`, а данные нужны.
3. **Сразу после** — `systemctl restart kotu`: на старте `ensureArchive` ставит триггеры заново
   (пересозданная таблица их теряет). До рестарта правки такой таблицы не архивируются; сам сервер
   заметит пропажу только при сверке раз в 6 ч.
4. Проверить `curl -s https://psy3107.ru/api/healthz` → `"archive":"ok"`.

### Откат

Если выкатка не приняла архив (`archive:"off"`) — сервер уже работает только на чтение, очередь стоит,
данные не меняются. **Ничего не откатывать и не чистить**: прислать вывод `deploy.sh` и журнал
(`journalctl -u kotu -n 200 --no-pager | grep -i архив`), чинить причину.

Откат на прежний код — **только с явного согласия владелицы**: код до 23.09.2026 без архива удаляет
аудио после расшифровки, чистит каталоги колод и пишет файлы на месте — он сам ведёт к потере данных.
И только **текущим** `deploy.sh` (снимок, проверка владельцев, опись) со старым кодом приложения:

```bash
git worktree add ../kotu-rollback <коммит>             # старый код отдельной копией
cp deploy.sh ../kotu-rollback/deploy.sh                 # но деплой и бэкап — нынешние
cp ops/kotu-backup.sh ../kotu-rollback/ops/kotu-backup.sh
cd ../kotu-rollback && pnpm install --frozen-lockfile && ./deploy.sh
```

(Нынешний `deploy.sh` у такого кода увидит `archive` не `ok` и остановится после рестарта — это ожидаемо.)

**Никогда** не запускать `deploy.sh` из старого коммита: прежние версии ротировали снимки
`/opt/backups/predeploy` через `rm -rf`. Копия прежнего кода в снимке (`<снимок>/code`) — для разбора,
а не для ручного `rsync --delete` поверх `/opt/kotu`.

## HTTPS и домен (2026-07-30)

- Платформа переехала на **https://psy3107.ru** (и www), сертификат Let's Encrypt до 28.10.2026, автопродление настроено certbot'ом
- nginx-сайт `psy3107`: статика + `/api` → 127.0.0.1:5010, редирект http → https, лимит загрузки 1 ГБ
- `PUBLIC_BASE_URL=https://psy3107.ru` в `/opt/kotu/.env` — от него зависит флаг `secure` у cookie сессии
- Старый адрес `http://5.129.198.180:8091` с 23.09.2026 только редиректит на https://psy3107.ru (`close-8091.sh`): по голому HTTP пароль и расшифровки шли открытым текстом, а войти там всё равно было нельзя — cookie сессии secure
- Грабля: `dig +short @сервер-реестра домен NS` НЕ показывает делегирование — записи приходят в секции AUTHORITY, короткий формат её не печатает. Проверять полным `dig` или через публичный резолвер

## Каналы к моделям (2026-07-30)

Транзит на дроплете стал многоканальным — через него доступны три поставщика:

| Путь на сервере (127.0.0.1:8444) | Куда идёт |
|---|---|
| `/v1/audio/*` | локальный Whisper — аудио не покидает РФ |

| `/perplexity/*` | Perplexity — поиск источников |

Ключи: `AI_INTEGRATIONS_OPENAI_API_KEY` (есть), `ANTHROPIC_API_KEY`, `GEMINI_API_KEY` — вводятся
скриптом `./set-ai-key.sh` (вслепую, с живой проверкой). Правило двух зон не меняется:
в эти каналы уходит только текст без персональных данных.
